# {{OWNER_NAME}} 的 Obsidian Vault — 給 Claude 的工作規範

這是 {{OWNER_NAME}} 的個人知識庫。任何時候在這個 vault 裡工作，都依照本檔規範。
本檔跟著 OneDrive 同步，換裝置後仍然有效。

## 使用情境（最重要）

{{OWNER_NAME}} 有兩種讀筆記的情境，每篇專案筆記都要同時滿足：

- **工作時** → 想看**系統結構**：架構、模組、資料流、相依。
- **工作外** → 想看**專案目的與需求**：為什麼做這個、解決什麼痛點、還缺什麼。用白話寫，不預設讀者記得技術細節。
- **心智圖** → 負責「結構與分布」的鳥瞰，用原生 Canvas。

## 語言與命名

- **內文繁體中文；檔名與 tag 用英文小寫連字號**（避免 OneDrive 路徑編碼問題）。
- 檔名格式：`<emoji> <kebab-name>.md`，emoji 後接一個半形空格。
- 屬性（frontmatter）欄位名一律英文，不自創欄位。
- **每篇筆記都要有中文標題**。英文 kebab 檔名只保證路徑安全，看不出內容，所以：
  - frontmatter 必填 `title:` — 一句看得懂的中文名（例：`維運整合平台 v2`）。
  - `aliases:` 補上常用別名（中文簡稱、英文原名、內部代號），讓搜尋與 `[[]]` 都找得到。
  - 內文 H1 寫成 `# <emoji> <中文標題>（<原始專案名>）`。
  - **心智圖節點一律顯示中文標題**，不可只放 kebab 檔名或 emoji。

## Emoji 分類規則

檔名開頭固定放**一個** emoji，代表這個專案的**領域**。
**只用一個 emoji**，不要疊加前綴——多個 emoji 會讓檔名更難掃（試過，{{OWNER_NAME}} 覺得更亂）。

| Emoji | `domain` | 用在什麼 |
| --- | --- | --- |
| 🌐 | `network` | 網路／設備／維運系統 |
| 🤖 | `ai` | AI／Agent／MCP／LLM 應用 |
| 🖥 | `platform` | 平台或系統開發（前後端＋DB 的完整應用） |
| 📊 | `data` | 報表、資料分析、log 處理、儀表板 |
| 🧰 | `tool` | 工具、腳本、CLI、自動化 |
| 🧪 | `lab` | 實驗場、練習、POC |
| 📐 | `plan` | 計畫、提案（**沒有程式碼**） |
| 💡 | `idea` | 靈感、構想 |
| 📚 | `research` | 研究、技術調查 |

> **前六個都是程式碼專案**，emoji 分的是領域不是性質。
> frontmatter 用兩個欄位表達：`kind: code`（或 plan / idea / research）＋ `domain:`（上表第二欄，僅程式碼專案有）。
> 要看領域分布就開 `99-bases/projects.base` 的「依 domain 分組」。

其他筆記類型：🗣 會議紀錄 ｜ 📌 需求 ｜ ⚖️ 決策 ADR ｜ 🗺 心智圖／索引。
每日筆記用純日期檔名，不加 emoji。

**wikilink 一律用純 slug**（例：`[[gss-log-doorman]]`），不要帶 emoji。
每篇筆記的 `aliases:` 第一項固定是純 slug、第二項是原始資料夾名，
這樣連結與 emoji 脫鉤，日後改 emoji 不會斷連結。

## 來源索引（建立專案時必做）

**每一篇專案筆記都必須有 `## 🧭 來源索引` 章節**，放在「📎 相關」之前。
沒有這一節就不算建立完成。

原因：筆記寫久了會分不出哪些是 {{OWNER_NAME}} 講的事實、哪些是外部查來的、哪些是我自己推的。
分不出來的後果是**我的推測會被當成事實引用**，而且錯了也追不到源頭。

### 三層分級

| 層級 | 定義 | 例子 |
| --- | --- | --- |
| **① 權威** | 專案本身或 {{OWNER_NAME}} 直接提供的一手資料 | repo 的 README／程式碼／git 歷史、GitLab API、{{OWNER_NAME}} 的交辦與回答、他提供的信件與附件 |
| **② 外部** | 公開可查證的第三方資料 | 官方文件網頁、廠商說明、規格書 |
| **③ 推論** | **我從既有資料推導出來的，沒有人證實過** | 跨專案關聯、用途猜測、把 A 專案的數據套用到 B 的情境、技術選型理由的臆測 |

### 格式

```markdown
## 🧭 來源索引

| 層級 | 來源 | 涵蓋了本篇哪些內容 | 取得日期 |
| --- | --- | --- | --- |
| ① 權威 | `README.md`（本機 clone） | 功能說明、架構圖、部署步驟 | 2026-08-19 |
| ① 權威 | git log（108 commits） | 時間軸、已完成項目、工作日誌 | 2026-08-19 |
| ② 外部 | <https://docs.example.com/...> | 版本相容性說明 | 2026-08-20 |
| ③ 推論 | 由 commit 命名與目錄結構推測 | 「與 X 專案的關聯」整段 | 2026-08-19 |
```

### 硬性規則

1. **③ 推論的內容在正文裡必須可辨識** —— 用「推測」「看起來」「應該」等字眼，
   或直接標 `（推論）`。**絕對不可以寫成肯定句。**
2. **沒有 ① 權威來源的專案要在最上方警告**，例如只靠資料夾名稱猜出來的專案。
3. **{{OWNER_NAME}} 回答待決事項後，該內容升級為 ① 權威**，並在來源索引補一列註明日期。
4. 素材（信件／PPT／Excel）進來時，**在來源索引加一列**，不要只寫進內文。
5. 專案內容被大幅改寫時（例如查證後推翻原本描述），**來源索引也要跟著更新**，
   並在工作日誌記一筆說明改了什麼、依據是什麼。

## 專案筆記固定結構

路徑：`10-projects/<emoji> <kebab-name>/<emoji> <kebab-name>.md`

frontmatter 必填：`type: project`、`kind`、`title`、`status`、`priority`、`owner`、`tags`。

**程式碼專案必須標記 git 資訊**（{{OWNER_NAME}} 是 programmer，這是找回原始碼的關鍵）：

| 欄位 | 取得方式 | 說明 |
| --- | --- | --- |
| `repo-path` | — | 本機絕對路徑 |
| `git-remote` | `git remote get-url origin` | 完整 URL，**GitHub 或 GitLab 都可能** |
| `git-host` | 從 URL 判斷 | `github` / `gitlab` / `other` |
| `git-namespace` | 從 URL 取 | 群組／擁有者路徑，例：`{{GITLAB_GROUP}}/sub-group`、`{{GITHUB_OWNER}}` |
| `git-branch` | `git rev-parse --abbrev-ref HEAD` | 目前分支（**不一定是 main**，另有 `master`、`dev-asiabay`、`python` 等） |
| `stack` | 讀 manifest／原始碼 | 技術棧陣列 |
| `start` | `git log` 最早一筆 | 起始日 |
| `last-commit` | `git log -1` | 最後提交日 |

沒有 git 的專案（例：`Azure-AI-platform`、`GSS-core`、`SourceCode(Portal)`）`git-remote` 寫 `none`，
並在「📎 相關」註明它不是版控專案。

「📎 相關」章節第一項固定放 git remote 的可點連結，第二項才是本機路徑。

**已知的 git 命名空間**（決定專案歸屬與 🔗 關聯圖的分群）：

- `gitlab.com/{{GITLAB_GROUP}}/` — 公司專案
  - 同一子群組內的 repo 視為同系列，彼此互連。
- `github.com/{{GITHUB_OWNER}}/` — 個人 GitHub
- 其他 host（例：`github.com/librenms/`）是**上游開源專案**，非 {{OWNER_NAME}} 所有，🔗 關聯圖要標明是 fork／上游。

章節順序固定：

1. `> [!abstract]` 一句話目標
2. `## 🎯 專案目的` — 白話，工作外看得懂
3. `## 📋 需求` — 已完成／待辦，用 checkbox
4. `## 🏗 系統結構` — 工作時看的那段
5. `## 🧠 心智圖` — 依序 embed 三張圖（結構／需求／相關），見下方心智圖規範
6. `## 🧭 來源索引` — **必填**，見上方「來源索引」章節
7. `## 📎 相關` — 原始碼路徑、文件、wikilink 到相關專案
8. `## ✉️ 信件討論` — 保留區，{{OWNER_NAME}} 會提供信件／PPT／Excel 讓我補
9. `## 🗒 工作日誌`

## 心智圖規範

**每個專案固定三張心智圖**，放在 `70-maps/<emoji> <kebab-name>/` 子資料夾裡：

| 檔名 | 類別 | 畫什麼 |
| --- | --- | --- |
| `🏗 <kebab>-arch.canvas` | **專案結構** | 系統架構、程式碼組織、模組分層、資料流、資料表。工作時看的那張。 |
| `📋 <kebab>-req.canvas` | **需求結構** | 已完成需求／待辦／待決事項、**會議討論與功能請求**的來源與去向，以及 **🤖 AI 建議**分支。 |
| `🔗 <kebab>-rel.canvas` | **其他相關** | 跟其他專案的關聯（同系列、上下游、共用元件）、素材文件、信件討論、相關的人。 |

三張都要遵守：

- **中心節點用 `text` 節點**，內容為 `# <類別 emoji> <類別名>` 換行 `## <中文標題>`，
  末行放 `[[<emoji> kebab-name|→ 開啟專案筆記]]`。
  不要用 `file` 節點當中心——縮小檢視時會渲染整篇內文，反而看不到標題。
- **每個節點都要有文字標題**：分支節點用 `# 標題`，葉節點用 `### 標題` 加一行說明。
  節點寬度給足（葉節點約 340–380），中文標題才不會被截斷。
- 顏色代碼：1 紅 2 橘 3 黃 4 綠 5 青 6 紫。中心節點用 5，待辦／風險用 1，待決用 2。
- 資訊還沒有的分支，放一個 `> [!info] 尚未關聯` 的節點佔位，不要留空分支。
- 專案筆記的「🧠 心智圖」章節要依序 embed 這三張。

### 🤖 AI 建議分支（`📋 req` 圖必備）

每張需求心智圖都要有一支 `# 🤖 AI 建議`，由我依專案現況主動提出功能建議與改善建議。規則：

- **一律條列式**，一個建議一個節點，節點內用 `### 標題` + 兩三行理由。
- 分成三組：`🚀 高投報（建議先做）`、`🏗 架構改善`、`💡 新功能構想`。
- **每則建議必須有依據**——引用專案裡的實際數字或事實（端點被幾個場景用、幾個檔案受影響、
  哪段程式碼會拋錯）。禁止寫「建議加強效能」這種沒有根據的空話。
- 建議節點用紫色（`"color": "6"` 的分支底下），與真實需求（紅色）在視覺上區隔。
- 分支標題節點要註明「**未經 {{OWNER_NAME}} 確認，僅供評估**」。
- 建議若對應到既有待辦或缺口，用 edge 連過去並標 `對應到` / `回答`。
- **{{OWNER_NAME}} 採納後**，才把該建議轉成 `type: requirement` 的需求筆記
  （見「需求與待辦的資料模型」），並在建議節點註明已轉需求。
- 專案筆記也要有對應的 `## 🤖 AI 建議` 章節，內容與心智圖一致。

`70-maps/` 根層另外放跨專案的總覽圖與 MOC 索引。

## 需求與待辦的資料模型（重要）

**待辦絕對不要只寫成 checkbox。** Markdown checkbox 是死文字，Bases 撈不到、無法跨專案彙整。
凡是需要被追蹤、被關聯、會出現在待辦清單上的項目，一律開成**獨立的需求筆記**：

- 位置：`10-projects/<emoji> <kebab>/requirements/📌 <REQ-ID>.md`
- `type: requirement`
- `project: "[[<emoji> kebab-name>]]"` ← **link 型屬性**，這條就是關聯的邊
- `source: "[[來源筆記]]"` ← 這條需求從哪來（場景庫／會議／信件）
- 其餘：`req-id`、`status`、`priority`、`owner`、`created`，可再加 `persona`、`support` 等領域欄位

這樣就能靠 Bases 做抽象關聯：

| Base | 作用 |
| --- | --- |
| `99-bases/todo.base` | **全域待辦清單**，撈所有 `status != done` 的需求，可依專案／優先序分組 |
| `99-bases/project-requirements.base` | 用 `file.hasLink(this)` 過濾，**embed 進專案筆記就只顯示該專案的需求** |
| `99-bases/requirements.base` | 完整需求總表 |

專案筆記的「📋 需求」章節用 `![[project-requirements.base]]` 嵌入，不要手寫清單。
只有還沒值得開成筆記的雜項才留 checkbox。

## 投放區（{{OWNER_NAME}} 直接丟檔案的地方）

{{OWNER_NAME}} 會把**信件（.eml / .msg）、Excel、PPT、Word、PDF、報告**直接丟在
**vault 根目錄**或 `00-inbox/`。這兩個位置就是投放區。

抽取工具：`.ops/venv/Scripts/python.exe .ops/extract_drops.py`
支援 `.eml`（stdlib）、`.msg`（extract-msg）、`.docx` / `.xlsx` / `.pptx`（zip+xml）、
`.html`（含挖出 script 內的 JSON）、純文字類。
`.pdf` 與圖片不抽取——那些用 Read 工具直接開。

**歸納完成後，原始檔搬到 `80-attachments/emails/`（信件）或 `80-attachments/`（其他），
根目錄與 `00-inbox/` 要清空**，並刪掉 `.ops/drops/` 的暫存抽取檔。
搬移而非刪除，是為了讓筆記裡的引用還找得到原件；{{OWNER_NAME}} 若要真刪，會明說。
**抽取失敗的檔案留在原地**，並在今日筆記說明原因。

## 外部素材處理流程

{{OWNER_NAME}} 會丟**報告、HTML、PPT、Excel、信件**給我，要我變成筆記。固定流程：

1. **先探勘，不要急著讀全文。** 檢查大小、格式，找出真正的內容在哪。
   HTML 尤其要小心：可見文字可能只有幾十行，**真正的資料常藏在 `<script>` 的 JSON 裡**
   （案例：`SI-Daily-Operations-v3.html` 表面 32 行，實際 283KB JSON、161 筆場景）。
2. **抽出結構化資料**，用腳本解析，不要把原始檔整份讀進上下文。
3. **產出兩種東西**：
   - **索引筆記** — 放進對應專案資料夾，含 frontmatter（`source`、`source-type`、`source-version`、`ingested`）、
     摘要、分布統計表、完整明細表。這是「這份素材講了什麼」。
   - **需求筆記** — 素材裡凡是**行動項目、缺口、功能請求**，拆成獨立的 `type: requirement` 筆記，
     `source:` 指回索引筆記。這是「所以我要做什麼」。
4. **原始檔位置**：已經在 repo 裡的（如 `docs/`）用路徑引用即可，**不要複製進 vault**。
   只有 repo 外的散檔（{{OWNER_NAME}} 直接給的信件、PPT）才放 `80-attachments/`。
5. **更新心智圖**：來源加進 `📋 req` 圖的「需求來源」分支，缺口加進「需求缺口」分支。
6. **回報數字**：告訴 {{OWNER_NAME}} 抽出幾筆、拆了幾則需求、有什麼是原本沒注意到的。

## 待決事項的處理方式

整理筆記時遇到無法從素材判斷的問題，**不要停下來問，也不要自行臆測當成事實**：

1. 寫進該專案筆記的 `> [!question] 待決事項` 區塊。
2. **同時**加進 vault 根目錄的 `❓ 待決事項.md` 總表，格式固定為
   `#### Qnn. 問題` ＋ `狀態` / `背景` / `未答時的預設` / `你的回答` 四行。
   「未答時的預設」要寫清楚沒有答案時會採取什麼假設，{{OWNER_NAME}} 才知道值不值得回。
3. 問題編號一旦給了就不要重編，{{OWNER_NAME}} 可能在別處引用。

**每次整理筆記前先讀這份總表**，處理 {{OWNER_NAME}} 已回答的問題。回答分三種：

| {{OWNER_NAME}} 的回答 | 怎麼做 |
| --- | --- |
| **陳述事實** | 落實到對應筆記（改描述、補關聯、更新 frontmatter 與心智圖、刪掉不成立的待辦） |
| **下達指示** | **直接執行**。做不到就在今日筆記說明卡在哪，該則保留並改狀態為 `⚠️ 已回答但未能執行` |
| **含糊或抒發** | 不要硬推論。保留該則、狀態改 `💬 已回覆但需再確認`，補一行說明還需要確認什麼 |

**處理完成後，把該則問題整段從 `❓ 待決事項.md` 刪掉**——不搬到「已解決」區、不留存根。
這份清單只該剩下還沒處理的東西。刪掉的問題與所做的事，記在當天的
`50-daily/YYYY-MM-DD.md`：`- Qnn「<問題摘要>」→ <回答摘要> → 已<做了什麼>，改動：<哪幾篇>`。

沒有回答的問題完全不要動。

## GitLab 寫入邊界（重要）

vault 的 token 具備寫入權，但**寫入分兩級**：

| 動作 | 誰可以做 | 為什麼 |
| --- | --- | --- |
| **在 issue 留言** | 每日排程可自動做 | 可逆、不發狀態變更通知，錯了直接更正 |
| **關閉 issue、改標題／標籤／指派** | **只有 {{OWNER_NAME}} 在對話中確認後** | 會發通知給相關同事，且判定是從 commit 推論的 |
| **開新 issue** | **只有 {{OWNER_NAME}} 在對話中明確要求時**（排程永遠不得開） | 會通知專案成員；開什麼、寫什麼由 {{OWNER_NAME}} 決定 |

工具是 `.ops/gitlab_write.py`：
- `comment` — 留言帶 `<!-- obsidian-vault-verify -->` 標記，重跑只更新既有留言不洗版
- `close` — 必須帶 `--allow-close`，**排程永遠不得帶**
- `create <project> <title> <md檔>` — 開新 issue；同標題已有 open issue 時回 `EXISTS` 不重開。不設標籤／指派（要設需另外確認）

留言內容一律要附 commit hash、日期與程式碼位置，並在結尾聲明「由自動化產生，不會自行關閉 issue」。

## 容器資料夾（不要當成專案）

`{{SOURCE_ROOT}}` 底下有些資料夾**只是容器**，裡面各自放著獨立的 repo，
**它們本身不是專案，不要為它們建筆記**。清單寫在 `.ops/config.json` 的
`container_dirs`，比對「有沒有新專案」時要跳過，否則每次都會誤報。

## 行動建議（與待決事項平級）

vault 根目錄有兩份平級的清單，**性質相反，不要混用**：

| 檔案 | 內容 | {{OWNER_NAME}} 要做什麼 | 生命週期 |
| --- | --- | --- | --- |
| `❓ 待決事項.md` | **我不能決定**、需要 {{OWNER_NAME}} 回答的問題 | 回答 | 答完整則刪除 |
| `🎯 行動建議.md` | **我建議 {{OWNER_NAME}} 做什麼**、以及怎麼做 | **什麼都不用做** | **每天整份重寫**，像當日新聞 |

判斷放哪一邊：**需要 {{OWNER_NAME}} 提供資訊或做決定才能推進的 → 待決事項；
已經可以動手、只是他還不知道的 → 行動建議。**

行動建議的三條鐵則（完整格式在 `.ops/daily-review.md` 步驟 1.5）：

1. **整份重寫**，不累積、不做狀態追蹤。某則連續出現時在標題後標 `（連續第 N 天）`，
   **只標註，不追問、不升級語氣**。
2. **不等裁示，也不自行動手。** 這份純粹是情報。
   絕對不要因為某則看起來正確就去改程式碼、改設定或在 GitLab 留言。
3. **每則要有可查證依據**（commit hash／檔案行號／需求編號／日期／數量）
   與**十分鐘內能動手的第一步**。想不出第一步就不要列。

分三區：🔴 最該看的（≤2）、🟡 值得排進這週（≤4）、⚪ 一句話帶過。
全部不超過 10 則；沒東西可寫就寫「今天沒有新的建議」，不要硬生。

## 注意事項

- vault 在 OneDrive 上且 Obsidian Sync 開著。**寫入前確認該檔沒有正在 Obsidian 裡編輯**，否則會產生衝突副本。
- 改 `.obsidian/` 設定時，若 Obsidian 正在執行，需請 {{OWNER_NAME}} 重啟才會生效。
- `.zip` 檔不納入 vault。
